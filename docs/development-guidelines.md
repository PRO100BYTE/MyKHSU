# Регламент разработки и качества

## Цель
Обеспечить предсказуемые изменения без регрессий и сохранить стабильность ключевых пользовательских сценариев, а также поддерживать высокое качество кода и документации.

## Обязательные принципы
1.  **Безопасность и корректность:** Изменения не должны приводить к уязвимостям или некорректной работе приложения.
2.  **Обратная совместимость:** Новые функции или изменения не должны нарушать работу существующих функций или данных.
3.  **Читаемость и поддержив��емость:** Код должен быть чистым, хорошо документированным и легко расширяемым.
4.  **Минимальность диффа:** Изменения должны быть сфокусированными и атомарными, чтобы упростить ревью и отладку.

## Рабочий процесс для любой задачи
1.  **Зафиксировать ожидаемый эффект для пользователя:** Чётко определить, что должно измениться и как это повлияет на пользователя.
2.  **Найти минимальную точку правки:** Определить наиболее локализованное место для внесения изменений.
3.  **Проверить связанные импорты/экспорты и соседние зависимости:** Убедиться, что изменения не затронут другие части системы неожиданным образом.
4.  **Внести атомарное изменение:** Выполнить одно небольшое, сфокусированное изменение за раз.
5.  **Добавить обработку ошибок в новые асинхронные ветки:** Обеспечить надёжность и предсказуемость поведения при ошибках.
6.  **Выполнить минимальную валидацию:** Проверить работоспособность изменений локально.
7.  **Описать результат, риски и ручные шаги проверки:** Подробно задокументировать изменения для других разработчиков и для целей тестирования.

## Требования к коду
*   Не добавлять тяжелые зависимости без явного запроса и обоснования.
*   Не переименовывать публичные сущности (компоненты, утилиты, константы) без необходимости и без обновления всех мест использования.
*   Не выносить большой рефакторинг в задачу, где нужен локальный фикс; для рефакторинга создавать отдельную задачу.
*   Не оставлять временные отладочные конструкции (например, `console.log`, закомментиров��нный код) в продакшн-коде.
*   Использовать линтеры и форматтеры (ESLint, Prettier) для поддержания единого стиля кода.

## Требования к обработке ошибок
*   Любая новая асинхронная ветка обязана иметь предсказуемый путь обработки ошибок (`predictable error path`).
*   Любые внешние данные (из API, локального хранилища) обязаны проходить валидацию на пустые, частичные или некорректные состояния.
*   UI должен иметь согласованные состояния `loading`/`empty`/`error`/`success` для всех асинхронных операций.
*   Ошибка не должна приводить к необратимой потере пользовательского состояния или краху приложения.

## Особые правила по зонам

### Расписание
*   Проверять переключение режимов день/неделя.
*   Проверять выбор курса/группы и корректную подгрузку данных.
*   Проверять оф��лайн-сценарий и корректный fallback на кэшированные данные.
*   Проверять экспорт расписания в PNG и календарь.

### Новости
*   Проверять фильтрацию, сортировку и дедупликацию новостей.
*   Проверять поведение при повторных обновлениях и пагинации.
*   Проверять оффлайн-сценарий и fallback на кэш.

### Карта
*   Проверять работу фильтров и корректную отрисовку маркеров на карте.
*   Проверять поведение при ошибках загрузки карты или данных.
*   Проверять работу кастомных нижних листов для фильтров.

### Настройки
*   Проверять сохранение и восстановление значений настроек.
*   Проверять, что изменение настройки корректно влияет на соответствующий экран/сервис (например, изменение темы).
*   Проверять работу переключателей для сплэша легенды и ан��мации конфетти.

## Поддерживаемый стек
*   **Expo SDK 58** и **React Native 0.88** (или выше, согласно актуальным версиям).
*   **iOS 26+**: Liquid Glass через `expo-glass-effect`, с fallback на `expo-blur` при недоступности API. Системные эффекты необходимо проверять на реальном устройстве и новой нативной сборке.
*   Проект использует **Continuous Native Generation**: каталоги `android/` и `ios/` не хранятся в репозитории и генерируются при сборке (`npx expo prebuild`).
*   После обновления нативных зависимостей или изменения нативной конфигурации следует выполнять `npx expo-doctor`; потребуется новая `development` или `production`-сборка.

## Минимальная валидация перед сдачей
*   Запуск приложения: `npm run start`.
*   Проверка измененного пользовательского сценария вручную на симуляторе/устройстве.
*   Проверка отсутствия синтаксических и импортных ошибок в затронутых файлах (ESLint).
*   Успешное прохождение всех автоматизированных тестов (если применимо).

## Расширенная валидация (если релевантно)
*   **Уведомления**: отсутствие дубликатов, корректный тайминг, правильное содержимое.
*   **Фоновые задачи**: отсутствие лишних частых запусков, корректная обработка ошибок.
*   **Хранилище**: корректное чтение старых значений после обновления схемы данных.
*   **Ассеты**: корректные пути и отображение на основных экранах и сплэш-экране.
*   **Разрешения**: корректный запрос и обработка разрешений для календаря и галереи.

## Формат отчетности по задаче
*   **Что сделано:** Чёткое и краткое описание выполненных изменений.
*   **Какие файлы изменены:** Список всех затронутых файлов.
*   **Почему выбран этот подход:** Обоснование принятых технических решений.
*   **Какие риски остаются:** Описание потенциальных проблем или нерешённых вопросов.
*   **Что проверить вручную:** Подробные шаги для ручного тестирования изменений.
*   **Co-authored-by:** Для совместных коммитов, указывать трейлеры `Co-authored-by: <name> <email>`.

# Развёртывание — MyKHSU Backend

## Требования

Для успешного развёртывания и работы бэкенд-сервиса "Мой ИТИ ХГУ" необходимы следующие компоненты:

*   **Операционная система:** Linux (например, Ubuntu 20.04 LTS или 22.04 LTS) или macOS. Windows также поддерживается для локальной разработки, но для продакшн-среды рекомендуется Linux.
*   **Node.js:** Версия 20.x или выше. Рекомендуется использовать менеджер версий Node.js (например, `nvm`) для удобного управления версиями.
*   **npm:** Версия 9.x или выше (поставляется с Node.js) или Yarn.
*   **Git:** Для клонирования репозитория и управления версиями.
*   **Свободное дисковое пространство:** Минимум 100 MB, так к��к размер SQLite баз данных может увеличиваться со временем.
*   **Nginx (опционально):** Для использования в качестве обратного прокси-сервера перед Node.js-приложением в продакшн-среде (рекомендуется для HTTPS и балансировки нагрузки).
*   **Docker и Docker Compose (опционально):** Для контейнеризированного развёртывания.

## Быстрый старт (локально)

Для быстрого запуска бэкенда на локальной машине выполните следующие шаги:

1.  **Клонирование репозитория:**
    ```bash
    git clone https://github.com/PRO100BYTE/MyKHSU-Backend.git
    cd MyKHSU-Backend
    ```

2.  **Установка зависимостей:**
    ```bash
    npm install
    # или
    yarn install
    ```

3.  **Настройка переменных окружения:**
    Создайте файл `.env` в корневой директори�� проекта, скопировав содержимое из `.env.example`.
    ```bash
    cp .env.example .env
    ```
    **Обязательно** отредактируйте файл `.env` и задайте значение для `JWT_SECRET`. Рекомендуется использовать длинную, случайную и сложную строку.
    ```ini
    # Пример:
    JWT_SECRET=your-very-long-random-string-at-least-64-characters
    ```

4.  **Создание директорий для данных и логов:**
    Бэкенд использует директории `data/` для SQLite баз данных и `logs/` для файлов логов. Создайте их, если они ещё не существуют:
    ```bash
    mkdir -p data logs
    ```

5.  **Инициализация администраторов:**
    Создайте начальных администраторов, используя скрипт `seed`. Пароли будут запрошены интерактивно, или их можно задать через переменные окружения.
    ```bash
    npm run seed
    ```

6.  **Сборка фронтенд-приложений (опционально):**
    Если вы планируете использовать админ-панель или веб-версию, соберите их:
    ```bash
    npm run build # Собирает админ-панель и веб-версию
    ```

7.  **Запуск сервера:**
    ```bash
    npm start
    ```
    Сервер будет запущен на порту, указанном в `.env` (по умолчанию `3000`).

## Продакшн (systemd / Ubuntu 24.04)

Для развёртывания бэкенда в продакшн-среде на базе Linux (например, Ubuntu 24.04) рекомендуется использовать `systemd` для управления сервисом. В репозитории уже подготовлен набор unit-файлов и вспомогательных скриптов, которые упрощают процесс развёртывания, запуска, мониторинга и автоматического обновления.

**Предоставленные unit-файлы и скрипты:**

*   `deploy/systemd/mykhsu-backend.service`: Основной unit-файл службы `systemd`, который определяет, как запускать и управлять Node.js-приложением. Он указывает путь к исполняемому файлу Node.js, рабочую директорию, пользователя, от имени которого запускается служба, и зависимости.
*   `deploy/systemd/mykhsu-backend-restart.service`: Вспомогательный unit-файл службы, который используется для выполнения перезапуска основного сервиса. Он может быть вызван вручную или по таймеру.
*   `deploy/systemd/mykhsu-backend-restart.timer`: Unit-файл таймера `systemd`, который периодически (по умолчанию, ежедневно в 04:30) запускает `mykhsu-backend-restart.service` для планового перезапуска и автоматического обновления приложения.
*   `deploy/systemd/mykhsu-backend-update-now.service`: Unit-файл службы для принудительного немедленного обновления приложения и перезапуска основного сервиса, независимо от расписания таймера.
*   `deploy/systemd/mykhsu-backend-update.sh`: Скрипт оболочки, который выполняет `git pull --ff-only`, `npm ci --omit=dev` и `npm run build` перед запуском/перезапуском сервиса. Он также содержит логику для пропуска обновления, если есть локальные незакоммиченные изменения.
*   `deploy/systemd/mykhsu-backend.env.example`: Пример файла переменных окружения, который будет использоваться службой `systemd`. Его необходимо скопировать и отредактировать для продакшн-среды.

Далее описаны шаги по настройке и запуску бэкенда с использованием `systemd`.

### 1) Подготовить системного пользователя и директории

Создайте системного пользователя `mykhsu`, от имени которого будет работать приложение, и директорию `/opt/mykhsu` для размещения кода приложения. Это обеспечивает изоляцию и безопасность.

```bash
sudo useradd --system --create-home --shell /usr/sbin/nologin mykhsu || true
# Создаёт системного пользователя 'mykhsu' без интерактивной оболочки и домашней директорией.
# '|| true' позволяет избежать ошибки, если пользователь уже существует.
sudo mkdir -p /opt/mykhsu
# Создаёт директорию для приложения, если она ещё не существует.
sudo chown -R mykhsu:mykhsu /opt/mykhsu
# Устанавливает владельца директории на пользователя 'mykhsu'.
```

### 2) Разместить приложение

Клонируйте репозиторий бэкенда в созданную директорию и установите все необходимые зависимости. Убедитесь, что вы используете URL вашего репозитория.

```bash
sudo -u mykhsu git clone https://github.com/PRO100BYTE/MyKHSU-Backend.git /opt/mykhsu/MyKHSU-Backend
# Клонирует репозиторий от имени пользователя 'mykhsu' в целевую директорию.
cd /opt/mykhsu/MyKHSU-Backend
# Переходит в директорию клонированного репозитория.
sudo -u mykhsu git submodule update --init --recursive
# Инициализирует и обновляет все Git-подмодули (например, MyKHSU-web).
sudo -u mykhsu npm ci --omit=dev
# Устанавливает продакшн-зависимости. 'npm ci' обеспечивает чистую установку, а '--omit=dev' исключает dev-зависимости.
sudo -u mykhsu npm run build
# Собирает фронтенд-приложения (админ-панель и веб-версию) для продакшн-использования.
```

**Примечание:** Сборочный скрипт `scripts/build-frontend.js` привязан к каталогу самого репозитория и не зависит от текущего `cwd` процесса, поэтому команда `sudo -u mykhsu npm run build` корректно работает и при запуске из `systemd`/Ubuntu-среды.

### 3) Настроить env-файл службы

Создайте директорию для конфигурационных файлов службы и скопируйте пример файла переменных окружения. Этот файл будет использоваться `systemd` для запуска приложения.

```bash
sudo mkdir -p /etc/mykhsu
# Создаёт директорию для конфигурации службы.
sudo cp /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend.env.example /etc/mykhsu/mykhsu-backend.env
# Копирует пример файла переменных окружения.
sudo chmod 600 /etc/mykhsu/mykhsu-backend.env
# Устанавливает права доступа, чтобы только root мог читать и писать в файл.
sudo chown root:root /etc/mykhsu/mykhsu-backend.env
# Устанавливает владельца файла на root.
```

**Важно:** Отредактируйте файл `/etc/mykhsu/mykhsu-backend.env` и обязательно задайте значение для `JWT_SECRET`. Это критически важная переменная для безопасности приложения.

Для включения автоматического обновления при каждом старте/рестарте службы убедитесь, что следующие переменные установлены:

```dotenv
MYKHSU_GIT_AUTOUPDATE=1
MYKHSU_GIT_BRANCH=main # Укажите вашу основную ветку
MYKHSU_APP_DIR=/opt/mykhsu/MyKHSU-Backend
```

**Полный список переменных окружения** с описанием можно найти в разделе [Переменные окружения (полный список)](#переменные-окружения-полный-список).

### 4) Установить unit-файлы

Скопируйте unit-файлы `systemd` в системную директорию и установите необходимые права доступа для скрипта обновления.

```bash
sudo cp /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend.service /etc/systemd/system/
# Копирует основной unit-файл службы.
sudo cp /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend-restart.service /etc/systemd/system/
# Копирует unit-файл для перезапуска службы.
sudo cp /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend-restart.timer /etc/systemd/system/
# Копирует unit-файл таймера для планового перезапуска.
sudo cp /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend-update-now.service /etc/systemd/system/
# Копирует unit-файл для принудительного обновления.
sudo chmod +x /opt/mykhsu/MyKHSU-Backend/deploy/systemd/mykhsu-backend-update.sh
# Делает скрипт обновления исполняемым.
```

### 5) Запустить службу

Перезагрузите конфигурацию `systemd`, включите и запустите основную службу бэкенда. Проверьте её статус и логи для подтверждения успешного запуска.

```bash
sudo systemctl daemon-reload
# Перезагружает конфигурацию systemd, чтобы она увидела новые unit-файлы.
sudo systemctl enable --now mykhsu-backend.service
# Включает службу для автоматического запуска при загрузке системы и запускает её немедленно.
sudo systemctl status mykhsu-backend.service
# Проверяет текущий статус службы.
sudo journalctl -u mykhsu-backend.service -f
# Просматривает логи службы в реальном ��ремени (нажмите Ctrl+C для выхода).
```

### 6) Включить плановый рестарт с автообновлением (опционально)

Для обеспечения актуальности приложения вы можете включить таймер `systemd`, который будет периодически перезапускать сервис. Перед каждым перезапуском будет выполняться скрипт обновления, который делает `git pull` и `npm ci`.

Таймер по умолчанию перезапускает сервис ежедневно в `04:30`.

```bash
sudo systemctl enable --now mykhsu-backend-restart.timer
# Включает и запускает таймер для планового перезапуска.
sudo systemctl list-timers | grep mykhsu
# Проверяет статус таймера.
```

**Важно:** Если в рабочем каталоге приложения (`/opt/mykhsu/MyKHSU-Backend`) есть локальные незакоммиченные изменения, автоматическое обновление будет пропущено (это защита от потери локальных правок).

### Ручн��е обновление через systemd

Вы можете вручную перезапустить службу или принудительно запустить процесс обновления.

*   **Перезапуск службы (с автообновлением):**
    ```bash
    sudo systemctl restart mykhsu-backend.service
    # Перезапускает службу. Перед стартом будет выполнен скрипт обновления.
    ```

*   **Принудительное обновление «прямо сейчас» (без перезапуска, если SHA не изменился):**
    ```bash
    sudo systemctl start mykhsu-backend-update-now.service
    # Запускает скрипт обновления. Если изменения есть, служба будет перезапущена.
    ```

## Nginx (обратный прокси)

В продакшн-среде рекомендуется использовать Nginx в качестве обратного прокси-сервера перед Node.js-приложением. Это позволяет обрабатывать HTTPS-трафик, управлять кэшированием, балансировать нагрузку и обслуживать статические файлы более эффективно. Бэкенд-сервер "Мой ИТИ ХГУ" на одном порту (по умолчанию `8080`) отдаёт сразу несколько типов контента:

*   `/api/*` и `/adminapi/*`: Основные API-эндпоинты для мобильного приложения и админ-панели.
*   `/admin-panel/*`: Статические файлы React-приложения админ-панели.
*   `/`: Статические файлы веб-версии MyKHSU-web.

Ниже приведён пример конфигурации Nginx, которая перенаправляет HTTP-трафик на HTTPS и проксирует запросы на Node.js-сервер.

```nginx
server {
    listen 80;
    server_name t2iti.khsu.ru; # Замените на ваш домен

    # Перенаправление HTTP → HTTPS для обеспечения безопасности
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name t2iti.khsu.ru; # Замените на ваш домен

    # Укажите пути к вашим SSL-сертификатам (например, от Let's Encrypt)
    ssl_certificate     /etc/letsencrypt/live/t2iti.khsu.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/t2iti.khsu.ru/privkey.pem;

    # Настройки SSL (рекомендуется для безопасности)
    ssl_session_cache shared:SSL:10m;
    ssl_session_timeout 1h;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers 'ECDHE-ECDSA-AES128-GCM-SHA256:ECDHE-RSA-AES128-GCM-SHA256:ECDHE-ECDSA-AES256-GCM-SHA384:ECDHE-RSA-AES256-GCM-SHA384:DHE-RSA-AES128-GCM-SHA256:DHE-RSA-AES256-GCM-SHA384';
    ssl_prefer_server_ciphers on;

    # Проксирование запросов на Node.js-сервер, работающий на 127.0.0.1:8080
    location / {
        proxy_pass         http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection 'upgrade';
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_cache_bypass $http_upgrade;
        proxy_read_timeout 30s;
    }

    # Ограничение размера тела запроса для загрузки файлов (например, расписания)
    client_max_body_size 50M;
}
```

**Пояснения к конфигурации:**

*   `listen 80` / `listen 443 ssl http2`: Nginx слушает стандартные порты HTTP и HTTPS.
*   `server_name`: Укажите доменное имя, по которому будет доступно ваше приложение.
*   `return 301 https://$host$request_uri`: Автоматически перенаправляет весь HTTP-трафик на HTTPS.
*   `ssl_certificate` / `ssl_certificate_key`: Пути к вашим SSL/TLS сертификатам. Рекомендуется использовать Let's Encrypt для бесплатных сертификатов.
*   `location /`: Блок, который определяет, как Nginx должен обрабатывать запросы. В данном случае, все запросы проксируются на внутренний Node.js-сервер.
*   `proxy_pass http://127.0.0.1:8080`: Указывает адрес и порт, на котором работает Node.js-приложение.
*   `proxy_set_header`: Эти заголовки необходимы для корректной работы Node.js-приложения за прокси-сервером, передавая информацию о реальном IP-адресе клиента, хосте и протоколе.
*   `client_max_body_size 50M`: Устанавливает максимальный размер тела запроса. Это важно для эндпоинтов, которые принимают большие файлы (например, загрузка JSON-файла расписания).

## Docker

Для контейнеризированного развёртывания бэкенда можно использовать Docker и Docker Compose. Это обеспечивает переносимость и упрощает управление зависимостями.

### Dockerfile

`Dockerfile` определяет, как собрать образ Docker для вашего приложения. Он включает установку зависимостей, копирование исходного кода и настройку среды выполнения.

```dockerfile
FROM node:20-alpine
# Используем официальный образ Node.js на базе Alpine Linux для уменьшения размера образа.

WORKDIR /app
# Устанавливаем рабочую директорию внутри контейнера.

COPY package*.json ./
# Копируем файлы package.json и package-lock.json для установки зависимостей.
RUN npm ci --only=production
# Устанавливаем только продакшн-зависимости. 'npm ci' обеспечивает детерминированную установку.

COPY src/ ./src/
# Копируем исходный код сервера.
COPY scripts/ ./scripts/
# Копируем вспомогательные скрипты.
COPY admin-panel/build/ ./admin-panel/build/
# Копируем собранные статические файлы админ-панели.
COPY web-build/ ./web-build/
# Копир��ем собранные статические файлы веб-версии.

RUN mkdir -p data logs
# Создаём директории для баз данных и логов внутри контейнера.

EXPOSE 8080
# Открываем порт 8080, на котором слушает Node.js-приложение.

CMD ["node", "src/index.js"]
# Определяем команду, которая будет запускаться при старте контейнера.
```

**Сборка Docker-образа:**

Перейдите в корневую директорию бэкенд-проекта и выполните:

```bash
docker build -t mykhsu-backend .
```

### Docker Compose

`docker-compose.yml` позволяет определить и запустить многоконтейнерные Docker-приложения. В данном случае он используется для запуска бэкенда и управления его томами и переменными окружения.

```yaml
# docker-compose.yml
version: '3.8'
services:
  mykhsu:
    build: .
    # Указывает Docker Compose собрать образ из текущей директории (используя Dockerfile).
    ports:
      - "8080:8080"
    # Проксирует порт 8080 контейнера на порт 8080 хост-машины.
    volumes:
      - ./data:/app/data
      # Монтирует локальную директорию 'data' в контейнер, чтобы SQLite базы данных сохранялись.
      - ./logs:/app/logs
      # Монтирует локальную директорию 'logs' для сохранения логов.
      - ./settings.json:/app/settings.json
      # Монтирует файл настроек, если он используется.
    environment:
      - PORT=8080
      # Устанавливает порт для Node.js-приложения внутри контейнера.
      - JWT_SECRET=${JWT_SECRET}
      # Передаёт JWT_SECRET из переменной окружения хост-машины.
      - PAIRS_DB_PATH=/app/data/pairs.sqlite
      # Указывает путь к базе данных расписания внутри контейнера.
      - USERS_DB_PATH=/app/data/users.sqlite
      # Указывает путь к базе данных пользователей внутри контейнера.
      - LOG_FILE_PATH=/app/logs/server.log
      # Указывает путь к файлу логов внутри конт��йнера.
    restart: unless-stopped
    # Автоматически перезапускает контейнер, если он остановился по любой причине, кроме явной остановки.
```

**Запуск с Docker Compose:**

Создайте файл `.env` в той же директории, что и `docker-compose.yml`, и укажите в нём `JWT_SECRET`:

```ini
JWT_SECRET=your-very-long-random-string
```

Затем запустите приложение:

```bash
docker compose up -d
# Запускает контейнер в фоновом режиме.
```

Для остановки:

```bash
docker compose down
# Останавливает и удаляет контейнеры, сети и тома, определённые в docker-compose.yml.
```

## Обновление с Go-версии (raspisanie)

Если вы мигрируете с оригинального бэкенда, написанного на Go (проект `raspisanie`), выполните следующие шаги для переноса данных и настройки Node.js-версии:

1.  **Перенос баз данных:**
    Скопируйте файлы `pairs.sqlite` и `users.sqlite` из директории оригинальной установки Go-бэкенда в папку `data/` вашего нового Node.js-проекта. Эти файлы содержат расписание и данные пользователей.

2.  **Перенос файла настроек:**
    Скопируйте файл `settings.json` (если он использовался в Go-версии) в корневую директорию Node.js-проек��а. Этот файл может содержать специфические настройки, которые могут быть полезны.

3.  **ВАЖНО: Формат хэшей паролей:**
    Формат хэшей паролей, используемый в Go-версии, отличается от формата, используемого в Node.js-версии.
    *   **В Go-версии:** Хэши генерировались с использованием `hex(argon2.IDKey(password, username, ...))`.
    *   **В Node.js-версии:** Используется стандартный Argon2id PHC-формат, предоставляемый npm-пакетом `argon2`.

    Из-за этого различия все существующие администраторы из `users.sqlite` **не смогут войти в систему** после миграции. Необходимо переустановить пароли для всех администраторов. Вы можете сделать это, запустив скрипт инициализации администраторов:
    ```bash
    npm run seed
    ```
    Этот скрипт позволит вам интерактивно задать новые пароли для существующих администраторов или создать новых.
